## The problem

The agency was already generating enquiries through Instagram.

The friction was what happened next.

A prospect might comment on a property post or send a direct message, but turning that enquiry into something the sales team could actually work meant replying, collecting the right information, interpreting what had been provided, creating the lead in HubSpot and making sure an advisor could take over.

The goal was not to add AI for the sake of it.

It was to remove the repetitive work between an Instagram enquiry and a CRM-ready lead without handing important decisions to automation.

I treated it as a workflow problem first and an AI problem second.

## What I owned

I designed and implemented the system from the business process through to production operation.

My work included mapping the enquiry journey, defining the automation boundary, designing workflow state, integrating Instagram and HubSpot, deciding where deterministic logic was sufficient, introducing AI only where interpretation added value, defining review paths, and building the monitoring and failure handling around the workflow.

I also operated and hardened the system after it went live.

Several of the strongest engineering decisions came from seeing how the workflow behaved against real enquiries rather than designing only for the happy path.

An eligible Instagram comment or direct message enters the workflow and is persisted before any action is taken.

The system checks whether the prospect is eligible and whether an intake is already active or complete. If not, it sends an approved request for:

Full name · Property interest · Contact number

The conversation then moves into a waiting state.

When the prospect replies, the workflow extracts the information it can, validates it and determines whether the lead is complete enough to continue.

A complete intake is written to HubSpot as a Contact and associated Deal, ready for a human advisor to follow up.

Anything outside the happy path follows an explicit route:

- Ambiguous input → Review
- Provider failure → Retry
- Repeated enquiry → Suppress safely
- Terminal failure → Incident

The workflow does not guess its way through uncertainty just to keep moving.

Most of this workflow does not require AI.

Eligibility, workflow state, duplicate prevention, validation, CRM writes, retries and recovery are predictable operations. They are handled deterministically.

The model is introduced only when the prospect's response is incomplete or ambiguous.

### Deterministic first

The workflow extracts anything that is explicit and normalises the fields it can identify reliably.

If the required details are already present, no model call is needed.

### AI as fallback

If context is still missing, the model is asked to infer only the missing information from the relevant conversation.

It is not given control over what happens next.

### Revalidation after AI

Model output is passed through validation again before the workflow continues.

If the result is valid and sufficiently confident, the lead can move into HubSpot.

If the information remains unclear or conflicting, the workflow keeps the conversation open or routes the case for review.

AI fills gaps. It does not own the workflow.

## Technical implementation

The workflow is built as a set of deliberately separated responsibilities rather than one large AI process.

Supabase stores durable workflow, prospect and CRM state and provides database-level safeguards around operations such as duplicate intake prevention.

Inngest handles asynchronous execution, scheduled health checks and recovery behaviour.

Composio provides authenticated access to external client systems.

Gemini is used as the extraction fallback when deterministic parsing leaves required context unresolved.

HubSpot receives the validated Contact and associated Deal once intake is complete.

The model is therefore one component inside the workflow rather than the workflow itself.

## Designing for production

Getting the workflow to respond to an Instagram enquiry was the straightforward part.

Real traffic exposed the more interesting engineering problems.

### One intake per prospect

Originally, separate Instagram events could create separate opportunities to send the intake request.

That works at an event level, but it is wrong at a business level.

The actual rule is:

One active or completed intake per prospect.

I moved the protection to prospect-level state and backed it with database safeguards so another event cannot accidentally create another customer message.

### Safe CRM retries

External writes cannot be treated as perfectly reliable.

HubSpot requests can fail, time out, hit rate limits or succeed while the worker loses confirmation of the result.

The workflow keeps durable CRM state and checks what already exists before repeating work.

Retries reconcile with existing state rather than blindly performing the same write again.

Never invent success. Never create the same record twice.

### Handling unexpected input

Real customers do not always respond in the requested format.

Some messages are incomplete. Some are ambiguous. Some contain unrelated information.

Deterministic validation runs first. AI is introduced only where interpretation is actually required.

If the resulting data still cannot be trusted, the workflow waits for more information or sends the case to a person rather than pushing uncertain data into the CRM.

## Selected engineering evidence

Three production changes became particularly important as the system matured.

### Prospect-level duplicate protection

The outbound intake rule moved from individual Instagram events to durable prospect state, preventing repeat interactions from triggering duplicate customer messages.

### Safe CRM concurrency

CRM work is protected against workers losing ownership while an external operation is still in progress. A stale worker cannot safely overwrite work subsequently owned by another process.

### Business-aware health checks

The monitoring system distinguishes a quiet Instagram account from genuine connection, webhook or delivery failure rather than treating lack of traffic as an outage.

These were not theoretical edge cases. They came from operating the workflow against real traffic.

### Failure needs somewhere to go

Recoverable failures retry automatically where it is safe to do so.

Failures that cannot be recovered automatically remain visible instead of disappearing into logs.

Incidents can be investigated and resolved once the underlying problem has been addressed.

The objective is not to make every failure autonomous.

It is to make sure the system fails visibly and predictably.

## What production taught me

### State beats events.

Business workflows care about the current state of the prospect or process, not simply how many webhook events have arrived.

### Monitoring needs business context.

No traffic and a broken integration are different operational states.

### AI belongs inside controlled systems.

Use models where interpretation helps and deterministic infrastructure where correctness matters.

## Outcome

During the first six live days, from 6 to 11 September 2026, the workflow handled:

- 42 Instagram comment replies
- 33 intake conversations
- 16 CRM-ready leads

Based on the agency's previous manual process, that represents approximately 5.5 hours of estimated repetitive team capacity released during the period.

More importantly, it moved beyond being a demo.

The system processed real conversations, created real CRM records, exposed real production edge cases and was hardened in response to them.

The sales team still owns the relationship with the prospect.

The workflow removes the repetitive work required to get that prospect into a state where a person can take over.
